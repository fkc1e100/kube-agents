# Security: Kubernetes RBAC

Part of [Security & IAM](../../site/src/content/docs/reference/security-and-iam.md).

## Kubernetes RBAC

Independently of the GCP permission set, the operator grants the agent KSA a **read-only** footprint on the Kubernetes API, plus one namespaced housekeeping Role. It creates three bindings (see [`platformagent_manifests.go`](https://github.com/gke-labs/kube-agents/blob/main/k8s-operator/internal/controller/platformagent_manifests.go)):

| Binding                                 | Role                       | Grants                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --------------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kubeagents:minimal:<namespace>:<name>` | custom minimal ClusterRole | Cluster-wide read access (`get`/`list`/`watch`) to audit resources (nodes, pods, deployments, configmaps, services, secrets, etc.), **excluding cluster RBAC** (while `<agent>-kube-proxy` strips Secret data fields). It also reads the GitOps reconcilers' sync objects (Argo CD Applications, Flux Kustomizations and Git and OCI sources, Config Sync RootSyncs and RepoSyncs), whose inline Helm values and substitutions it can therefore read. |
| `kubeagents:local:<namespace>:<name>`   | custom namespaced Role     | Read access (`get`/`list`/`watch`) to `PlatformAgent` CRs in the agent's **own namespace only**.                                                                                                                                                                                                                                                                                                                                                      |
| `kubeagents:leader:<namespace>:<name>`  | custom namespaced Role     | Housekeeping in the agent's **own namespace only**: write on `coordination.k8s.io` `leases` (leader election), plus `get`/`patch` on `pods` only above one replica, which the operator does not render today.                                                                                                                                                                                                                                         |

For the default CR (`platform-agent` in `kubeagents-system`) the bindings resolve to `kubeagents:minimal:kubeagents-system:platform-agent`, `kubeagents:local:kubeagents-system:platform-agent`, and `kubeagents:leader:kubeagents-system:platform-agent`.

The Kubernetes `minimal` and `local` roles carry no write verbs (`create`, `update`, `patch`, `delete`) and grant no read access to cluster RBAC. On a new install, the `minimal` role grants `get`/`list`/`watch` on `secrets` by default so `<agent>-kube-proxy` serves redacted Secret metadata while `KUBE_PROXY_REDACT_SECRETS=true` strips `.data`, `.stringData`, and `kubectl.kubernetes.io/last-applied-configuration`. (The GCP IAM `read-only` permission set independently provides cluster-viewer read via Cloud IAM for audits connecting through `gcloud container clusters get-credentials`.)

The `kubeagents:minimal:<namespace>:<name>` binding covers the agent ServiceAccount and the gateway ServiceAccount (`<agent>-gateway-agent`). Model-executing containers mount no default-audience token and reach the API server through `<agent>-kube-proxy`, while the broker command policy refuses `Secret` reads on `/v1/exec` and `agent-api-auth` uses its token only for event and CR watches. It also reads the cluster JWKS with it, to verify the broker's token at the audit-report store listener. When `spec.security.disallowSecretsRead` is unset on an existing install, the operator preserves the `secrets` permission on `kubeagents:minimal:<namespace>:<name>`. Set `spec.security.disallowSecretsRead: true` (`--disallow-secrets-read=true` in `install.sh`) to omit `secrets`, or `false` to add `secrets` on an upgraded install.

The only write grant anywhere in Kubernetes RBAC is the `leader` Role, and it is confined to the agent's own namespace: leader-election `leases`, plus `get`/`patch` on `pods` there when the deployment resolves to more than one replica. The leader labels its own pod so the Service routes to it; at one replica that code never runs and the rule is not rendered. The count that matters is the effective one: the operator caps the gateway at one replica whatever `spec.deployment.availability.replicas` asks for (the `ReplicasLimited` condition reports it), and `spec.deployment.scaleToZero: true` resolves to zero, so no install renders the `pods` rule today.

The agent cannot modify Deployments, Services, or namespaces, and it cannot read Secret values. If a resource it proposes needs a Secret, it references the Secret by name rather than reading its contents.

Verify the bindings on a running cluster:

```bash
kubectl describe clusterrolebinding kubeagents:minimal:kubeagents-system:platform-agent
kubectl describe rolebinding -n kubeagents-system kubeagents:local:kubeagents-system:platform-agent
kubectl describe rolebinding -n kubeagents-system kubeagents:leader:kubeagents-system:platform-agent
```

### The admission backstop on agent RBAC

The RBAC above is what the operator creates. Alongside it, two cluster-scoped `ValidatingAdmissionPolicy` objects reject some agent RBAC at apply time, whoever applies it. One source, [`k8s-operator/config/admission/agent-rbac-policy.yaml`](https://github.com/gke-labs/kube-agents/blob/main/k8s-operator/config/admission/agent-rbac-policy.yaml), and which installs apply it depends on how you install:

| Install method                                                                | Ships the policies?                                                                                                                                     |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The install engine — `install.sh`, or Terraform + Helm directly (Methods 0/1) | **Yes on Kubernetes 1.30+** — `templates/agent-rbac-admission-policy.yaml`, gated on `admissionPolicy.enabled` (default on) and on the cluster version. |
| Manual `make install && make deploy` (Method 2)                               | **No** — apply the source yourself; INSTALL.md Method 2 Step 4 has the command.                                                                         |

They are outside the kustomize overlay on purpose: its `namePrefix` rewrites each policy's name but not the `spec.policyName` its binding refers to, which would leave the bindings pointing at nothing and the policies inert with no error. A plain `kubectl apply` has no such transform.

They need Kubernetes 1.30 or later, where the policy API reached `v1`. The chart template checks the cluster's version as well as the values gate, so on 1.29 it renders nothing rather than failing the install. That also means an install there is not backstopped at admission and nothing says so at the time.

**What they govern is narrower than "agent RBAC", and the gap is worth knowing before you rely on them.** Policy 1 selects only objects carrying the `kube-agents/tier` label. Nothing the operator creates carries it — the operator stamps the four `app.kubernetes.io/*` labels and no tier — so on a default install with no GitOps overlay, **policy 1 matches nothing at all**. It is a backstop on the RBAC your overlay writes, not on the RBAC the operator mints. Policy 2 does see the operator's `kubeagents:minimal:*` ClusterRoleBinding, whose subject ends in `-agent`, and deliberately exempts it: the operator has no namespace-tier path, so the one case policy 2 denies is one it cannot produce.

| Policy                            | Governs                                                                          | Denies                                                                                                             |
| --------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `kube-agents-agent-readonly`      | `Role` / `ClusterRole` labelled `kube-agents/tier`                               | Any verb outside `get`/`list`/`watch`; any rule reaching `secrets`; a `ClusterRole` for the `developer-team` tier. |
| `kube-agents-agent-binding-scope` | `RoleBinding` / `ClusterRoleBinding` whose subject is a `*-agent` ServiceAccount | A `ClusterRoleBinding` to `developer-team-agent`.                                                                  |

What they do **not** cover, stated plainly because a backstop misread as complete is worse than none:

- **They cannot check the role a binding points at.** CEL in a `ValidatingAdmissionPolicy` sees only the object being admitted, so an unlabelled write `Role` bound to an agent ServiceAccount is admitted. Closing that needs a cross-object webhook, which is not built.
- **The content policy is label-selected.** `kube-agents-agent-readonly` only looks at objects carrying `kube-agents/tier`. A hand-written manifest that omits the label is not examined at all; pull-request review is what catches that. The binding-scope policy is not evadable that way: it keys on the ServiceAccount being privileged, which the binding cannot omit.
  - Nor is it evadable by _adding_ something: its one exemption, for the operator's own reconcile, matches on `request.userInfo.username`, which the API server fills in from the authenticated request and no manifest can carry. That distinction is load-bearing rather than pedantic: `matchConditions` are ANDed, so a false one drops the object from the policy altogether. An exemption an author could satisfy from inside the manifest would be a bypass of the whole rule rather than a carve-out from it.
- **Policy 2 denies exactly one ServiceAccount name.** A cluster-scoped binding to any other agent ServiceAccount is admitted. Combined with the label point above, this means an unlabelled `ClusterRole` granting `*` on `*`, bound to the agent's own ServiceAccount, is admitted by both policies on a default install. Pull-request review on the GitOps repository is the control for that, which is what the [branch-protection guidance](https://github.com/gke-labs/kube-agents/blob/main/examples/gitops-repo/.github/branch-protection.md) shipped with the example overlay is for.
- **Policy 2 only examines `kind: ServiceAccount` subjects.** A binding whose subject is a `kind: Group` — `system:serviceaccounts:team-x`, say — is not selected. The subject is unforgeable for the kinds the policy looks at; choosing a different kind steps outside them.
- **They govern agent RBAC, not the operator's own.** The controller's ClusterRole and Role below are unlabelled and out of scope by design.

### The admission policy on the A2A gateway's pods

The A2A gateway creates session pods (one per delegated task, or one per conversation on the session route), so its Role allows `create` on pods in its namespace. RBAC cannot limit what such a pod runs as. A third `ValidatingAdmissionPolicy`, `kube-agents-a2a-gateway-pod`, holds every pod the gateway's ServiceAccount creates to the session pod shape:

- It runs as the session ServiceAccount, `<name>-a2a-session`, which holds no RBAC.
- `automountServiceAccountToken` is `false`, and its projected tokens are only for the bus and the credential broker's session audience.
- It mounts no Secret and no host path, uses no host namespace, host port or fixed node, and runs no init container.
- It may read one Secret into its environment and no other: `ANTHROPIC_API_KEY` from key `api-key` of `<name>-inference-key-a2a-session`, the session's inference key, not marked optional. No `envFrom` from a Secret. The name follows the gateway's own, so one agent's gateway can't hand its session pods another agent's key.
- It meets Pod Security "restricted": non-root, seccomp `RuntimeDefault`, no added capabilities, no privilege escalation, and no `Unconfined` AppArmor.
- It carries exactly the session labels, so the session network policies select it and no other workload's policies or Services do.
- It leaves scheduling alone: no runtime class, node selector, affinity or positive priority, and no scheduler or toleration beyond those the API server and GKE add to every pod. A default PriorityClass with a positive value, a default GKE ComputeClass (which adds a node selector to every pod), or any other mutating webhook that adds a scheduling field, refuses every session pod.

The source is [`k8s-operator/config/admission/a2a-gateway-pod-policy.yaml`](https://github.com/gke-labs/kube-agents/blob/main/k8s-operator/config/admission/a2a-gateway-pod-policy.yaml). The chart installs it on the same terms as the two policies above: `admissionPolicy.enabled` and Kubernetes 1.30 or later. Method 2 applies it by hand. Where the chart installs it, the chart also sets `A2A_GATEWAY_POD_POLICY` on the operator. It is a signal for operator features that must run only where this policy is installed, and it says the policy was rendered, not that it still holds.

It does not cover an install where it is not applied: there, the gateway's `create` on pods is as wide as its Role. It selects the gateway by its ServiceAccount name, `<name>-a2a-gateway`.

### The admission policy on the web console's writes

The [web console](../../site/src/content/docs/deploy/web-console.mdx)'s ServiceAccount holds `get` and `patch` on the `PlatformAgent`, and RBAC cannot limit `patch` to fields. A fourth `ValidatingAdmissionPolicy`, `kube-agents-web-console-cr`, refuses any update by that ServiceAccount that changes something other than the console's own `kubeagents.x-k8s.io/` annotations and `spec.integration.forges`, `repositories` and `github`. The rest of the spec, the chat integrations' settings among it, and the labels, finalizers and owner references stay out of the console's reach.

The source is [`k8s-operator/config/admission/web-console-cr-policy.yaml`](https://github.com/gke-labs/kube-agents/blob/main/k8s-operator/config/admission/web-console-cr-policy.yaml). The chart installs it with `admissionPolicy.enabled` on Kubernetes 1.30 or later, where the console and its environment page are on. It selects the console by its ServiceAccount name, `<release>-web-console`.

Inside `forges`, it keeps each existing forge's host, port, scheme, provider, `credentialsRef`, `caBundleRef` and `identity`, and the namespace of a forge with a `credentialsRef`. A forge the console adds may carry no `credentialsRef` or `caBundleRef`, and a GitHub forge it adds must sit at a host a GitHub forge already uses. The install's GitHub host, where the broker spends the GitHub App token, stays as it is.

While the declaration has a forge the operator refuses in a way that could move that host, the console may not change `forges` at all until an administrator fixes it. The same holds while GitHub forges name two different CA bundles, because the broker trusts the first one's for that host. Adding a repository on a forge with a credential still widens the paths that forge's token may reach.

### The operator controller is a separate identity

Everything above describes the _agent_. The controller-manager that reconciles `PlatformAgent` CRs runs under its own KSA: `kubeagents-controller` on a kustomize install, `<release>-operator-sa` on a Helm install. Its permissions are the `+kubebuilder:rbac` markers in the controller. `make manifests` renders them into [`k8s-operator/config/rbac/role.yaml`](https://github.com/gke-labs/kube-agents/blob/main/k8s-operator/config/rbac/role.yaml) as two objects, which the chart copies: a ClusterRole, and a Role (`kubeagents-manager-role` under kustomize, `<release>-operator-namespaced-role` under Helm) bound in the install namespace and in the profile namespace (`<install namespace>-profiles`). Each marker carries the reason its rule exists; this section gives the same reasons in prose.

**Every write verb on a namespaced kind is the Role, and the ClusterRole holds reads.** The controller writes each kind it renders in two namespaces only: the namespace of the `PlatformAgent` it reconciles, which both install paths make the install namespace, and that namespace's profile namespace. The Role carries `create`, `update`, `patch` and `delete` on every one of them. Those are Secrets, ConfigMaps, ServiceAccounts, Services, PVCs, Pods, ResourceQuotas, Deployments, StatefulSets, Jobs, Leases, NetworkPolicies, FQDNNetworkPolicies, PodDisruptionBudgets, Roles and RoleBindings, and the dispatcher's `DispatchJobTemplate` params. It also carries `create` and `patch` on Events and the `create`-only dry run of PodTemplates. A RoleBinding binds it in each namespace, and the ClusterRole carries no write verb on any of them.

The read verbs (`get`, `list`, `watch`) stay in the ClusterRole, cluster-wide, for two reasons. The controller watches the rendered kinds it caches through cluster-wide informers for drift. And the agent's `minimal` role above grants cluster-wide reads, which Kubernetes refuses to let a subject grant without holding them; Jobs, ResourceQuotas, Pods and Secrets, which the controller reads uncached or by name, keep their reads for that reason alone. No read verb is in the Role: a read there is refused wherever the Role is not bound, and the controller reads the dispatcher's `DispatchJobTemplate` params in a profile namespace.

The controller itself reads Secrets by name only. Controller code never starts a Secret informer or lists Secrets, and [`tests/test_operator_secrets_grant.py`](https://github.com/gke-labs/kube-agents/blob/main/tests/test_operator_secrets_grant.py) fails if that changes; the same file pins the verb set of each document in `role.yaml`, and the chart's copy is held to it by `make chart-check`.

The validating webhook, where it is enabled, refuses a `PlatformAgent` created in any namespace but the operator's own, naming that namespace and this Role as the reason. One that exists in another namespace anyway, created while the webhook was off, needs the same Role and RoleBinding there and in `<that namespace>-profiles`. Without them its reconcile fails on the first write with `forbidden`, and the controller reports `Degraded`/`RBACIncomplete` on that agent naming the namespace. An update of it is admitted with a warning that names both namespaces. A profile namespace made by hand on a kustomize install needs them too; `make deploy` applies `config/profiles`, which carries them.

What the controller does with those verbs: on every install it **reads the values** of the Secret keys the agent pod consumes as environment. It digests them onto the pod template, so that rotating one rolls the pod ([PlatformAgent CRD](platformagent-profile-config.md#rotating-a-secret-rolls-the-pod)). Which Secrets those are is decided by the rendered pod spec, so a CR-supplied or plugin-supplied `SecretKeyRef` widens it to that Secret too. The digest is an HMAC-SHA256 keyed by the UIDs of the Secrets read, so the annotation cannot be used to verify guesses at a value. The controller also asks whether the shell sandbox's authorized-keys Secret exists, without reading it, and it creates and renews the kube-proxy TLS Secret on every install.

The controller creates and repairs the Secrets it generates for the A2A stack: the NATS credentials, config and TLS certificates, the callout and task-signing keys, the door and inject tokens, and the MCP access token. Every read is by name and uncached.

**Every rule in the ClusterRole is there for one of four reasons.** The _custom resources_ (`PlatformAgent`, `AgentPlugin` and `AgentProfile`, with status and finalizer subresources where they have them) are watched and written in every namespace, because nothing fixes the namespace a CR is created in. The _rendered kinds_ are what the controller creates for an agent, in the agent's namespace or its profile namespace, and watches cluster-wide for drift; the ClusterRole holds their reads and the Role their writes. They are Deployments and StatefulSets, ServiceAccounts, Services, ConfigMaps, PVCs, Pods (the A2A session pods), NetworkPolicies and FQDNNetworkPolicies, PodDisruptionBudgets, leases, `batch` Jobs (the bus provisioning run), ResourceQuotas (the session-pod bound), and the agent's Roles and RoleBindings.

The dispatcher's `DispatchJobTemplate` (a fourth custom resource, written by the operator alone) is a rendered kind too: its `get` and `list` are in the ClusterRole like the others', its writes in the Role. The `create`-only dry run of PodTemplates that defaults it is in the Role alone. Each verb the controller writes a custom resource with has a caller, and the controller never creates or deletes a `PlatformAgent`, so those two verbs are not granted. Events are `create` and `patch` in the Role, for the Warnings it records on the `PlatformAgent` ([CRD reference](../../site/src/content/docs/operator/platformagent-crd.md#status)).

The _escalation-prevention reads_ are read-only grants the controller holds for the agent's sake. Kubernetes refuses to let a subject grant a permission it does not hold, and the agent's audit ClusterRole above grants cluster-wide reads, so the controller holds the same reads in order to apply that role. Those are nodes, namespaces, PersistentVolumes, pod logs, events (reads), Secrets (reads, as above), DaemonSets and ReplicaSets, metrics, HorizontalPodAutoscalers, CronJobs, Ingresses, RuntimeClasses and CRDs. The GitOps reconcilers' sync objects are in the same set: Argo CD Applications, Flux Kustomizations and Git and OCI sources, Config Sync RootSyncs and RepoSyncs. `tokenreviews: create` is held for the same reason: the controller grants it to the split credential broker.

Three of these the controller also reads itself: a DaemonSet, by name, for its port; the callout's ReplicaSets, listed in its namespace; and the Secrets named above, by name.

The _controller's own reads_ are the few it does by name or in one namespace. They are the agent namespace's LimitRanges for sizing, the `kubernetes` Endpoints for the egress policy, a RuntimeClass to validate the sandbox's, and a StorageClass (`get` only) to learn whether a data claim can expand. It also gets the A2A bus StatefulSet's ControllerRevisions (`get` only) to tell which AgentProfiles every bus server has loaded. The dispatcher Job's admission policy and its binding are read by name (`get`) to confirm they are in place.

**The RBAC rule is bounded by the escalation check, not by names.** The controller holds every verb on ClusterRoles and ClusterRoleBindings, and unscoped `list` and `watch` on Roles and RoleBindings. It writes the per-agent objects named above: `kubeagents:minimal:<namespace>:<name>`, `kubeagents:tokenreview:<namespace>:<name>` and `kubeagents:a2a-callout-tokenreview:<namespace>:<name>` cluster-wide, plus the namespaced local, leader, gateway, callout, dispatcher and scope-publisher roles. Every name carries the agent's namespace and name, so `resourceNames` cannot pin them, and the informers that watch them for drift need unscoped `list` and `watch`. What bounds the grant is the API server's escalation check: no subject may author or bind a role conferring permissions it does not itself hold. The controller holds no `escalate`, the verb that waives the check.

One cluster-scoped permission reaches past that: `bind` on the built-in `system:auth-delegator` ClusterRole, granted by name. It lets the controller bind the A2A auth callout's ServiceAccount to that role, which is what permits the callout to create TokenReviews and so validate the ServiceAccount tokens bus clients present. It ships on **every** install. `bind` is one of the three RBAC verbs that let a subject hand out authority it does not exercise itself (`bind`, `escalate` and `impersonate`). Held here in its resourceNames-scoped form, it permits granting that one role and confers none of its permissions on the controller.

It is needed because `system:auth-delegator` also carries `subjectaccessreviews: create`, which the controller does not hold; without `bind` the API server refuses the binding with `attempting to grant RBAC permissions not currently held`. Binding the role kube-apiserver ships is the conventional pattern for a TokenReview client and keeps the grant auditable by name. A narrower alternative, a controller-authored ClusterRole carrying only `tokenreviews: create`, is not what ships today.

The controller verifies at startup, and every five minutes after on its own ticker, that the roles bound to it grant every permission the markers declare. The namespaced write verbs are probed in its own namespace, in the namespace of every `PlatformAgent` it reconciles, and in that agent's profile namespace once it exists; the rest cluster-wide. A shortfall is reported as a `Degraded`/`RBACIncomplete` condition on each `PlatformAgent`, the signature of an image deployed ahead of its manifests; the [operator page](../../site/src/content/docs/operator/index.md#an-image-ahead-of-its-clusterrole) has the cadence and the `make deploy` guard that prevents it. Verify the shape on a running cluster:

```bash
# The Helm install's controller; a kustomize install's is kubeagents-controller.
SA=system:serviceaccount:kubeagents-system:kube-agents-operator-sa
kubectl auth can-i create secrets --as="$SA" --all-namespaces              # no
kubectl auth can-i create deployments.apps --as="$SA" --all-namespaces     # no
kubectl auth can-i create secrets --as="$SA" -n kubeagents-system          # yes
kubectl auth can-i create deployments.apps --as="$SA" -n kubeagents-system-profiles  # yes
kubectl auth can-i get secrets --as="$SA" --all-namespaces                 # yes: the reads the agent's minimal role needs
kubectl auth can-i list deployments.apps --as="$SA" --all-namespaces       # yes: the informers
kubectl get role,rolebinding -A -l app.kubernetes.io/name=kube-agents-operator
```

Unlike the agent, the controller has no GCP identity: no install path creates a controller GSA or Workload Identity binding for it.

### The Vertex AI gateway is a separate identity

With `MODEL_PROVIDER=vertex_ai` the LiteLLM gateway gets its own KSA (`kubeagents-litellm`) bound to its own GSA (`kubeagents-litellm-gsa`), holding exactly one role, `roles/aiplatform.user` on the serving project, and nothing else. It is deliberately not the agent's identity: the gateway is a network-exposed proxy that forwards attacker-influenceable prompt content, so it is scoped to calling models and cannot touch GKE, logging, or the GitOps path.

With `model_provider = "vertex_ai"` the `full-install` composition instantiates the [`kube-agents-iam`](https://github.com/gke-labs/kube-agents/tree/main/terraform/modules/kube-agents-iam) module a second time for the gateway (the GSA, `roles/aiplatform.user` on the serving project, and the Workload Identity binding), and the Helm chart renders the annotated KSA. Because the pair is Terraform-managed, switching away from `vertex_ai` removes it on the next apply and leaves no orphan. The exception is an install with `VERTEX_MANAGE_SERVING_PROJECT=false`, for a serving project the installing identity cannot administer: there the operator makes the `roles/aiplatform.user` grant by hand, Terraform never owns it, and the operator removes it.

On clusters without Workload Identity, a chart install can instead set `litellm.vertex.credentialsSecretRef` to mount a static GCP service-account key at `/var/run/secrets/vertex/sa.json` via `GOOGLE_APPLICATION_CREDENTIALS`. It can also set `litellm.vertex.projectSecretRef` for `VERTEXAI_PROJECT`, and the mounted key takes precedence over the KSA's Workload Identity binding.

In that mode Terraform does not manage the key's service account or its bindings, and nothing in the chart restricts what roles that account holds. The operator must mint the key for a dedicated service account holding only `roles/aiplatform.user` on the serving project (never the agent's own GSA) and rotate or revoke the Secret when switching providers. Rotating the Secret does not roll the gateway; restart it with `kubectl rollout restart deployment/litellm -n kubeagents-system`.

The other providers give the gateway no GCP identity at all. It authenticates with an API key from `platform-agent-secrets`. For `sap`, any other LiteLLM provider slug and an `openai_compatible` gateway behind OAuth2 client credentials, it uses the contents of a Secret you create and name with `--litellm-env-secret`, which the install never creates, stores or rewrites ([the credentials Secret](../../site/src/content/docs/concepts/inference-litellm.md#a-credentials-secret-for-the-gateway)). With `openai_compatible` the key is optional and is read from `OPENAI_COMPATIBLE_API_KEY` in `platform-agent-secrets`, and the gateway pod receives none of the Gemini, OpenAI or Anthropic keys, so nothing it sends to your server can carry one.

### What leaves for the model provider

Callers authenticate to the gateway by key. Its master key, in the `litellm-master-key` Secret the chart generates, is read by the gateway container alone and is the only key that reaches LiteLLM's admin routes. Any other caller reaches the inference routes only, admitted as the caller class its key names, or as `keyless` when it sends no key or a placeholder; an unknown key is refused. [Caller authentication](../../site/src/content/docs/concepts/inference-litellm.md#caller-authentication) has the rules.

The gateway is the one point every provider request transits, and the chart can make it redact those requests. `litellm.redaction.enabled=true` (`LITELLM_REDACTION_ENABLED=true` in `install.env`, or the Terraform example's `litellm_redaction` variable) runs the shared `AuditRedactor` as a LiteLLM pre-call hook. It masks the built-in credential shapes and masks or pseudonymises IP literals and any operator-named identifiers before the body leaves the cluster. It is off by default, and it covers request bodies and, through the same switch, the files the agent writes to its volume (below). A pseudonymised identifier is one the agent can no longer act on; [Inference gateway](../../site/src/content/docs/concepts/inference-litellm.md#redaction-at-the-gateway) owns the rules, the actions and that limitation.

### Egress when model data must stay off hosted providers

With `MODEL_PROVIDER=openai_compatible` every model request goes from the gateway to a server you run, and the gateway's NetworkPolicy gains one rule, derived from that server's URL. The rule names the server's namespace on its pod port for an in-cluster Service, or the CIDRs you list on the URL's port for a private address ([Inference gateway](../../site/src/content/docs/concepts/inference-self-hosted.md#egress-to-the-server) has the forms). That keeps prompts off a hosted model. It does not make the install offline. A fully disconnected cluster is not supported: Google APIs have to be reachable, and [Private Google Access](https://cloud.google.com/vpc/docs/private-google-access) is enough for that. Its `private.googleapis.com` and `restricted.googleapis.com` ranges are outside the private ranges the generated policies exclude, so their existing 443 rules already reach them.

What else leaves the cluster, and whether you can turn it off:

| Destination                                                                                  | Who calls it                                                                                                                                                      | Required | How to turn it off                                                                                                                                                                                                                                                                                            |
| -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

Use Private Google Access.                                                                                                                                                                                                                                                              |

### Each A2A session pod is its own bus identity

[`docs/designs/spec-nats-deployment.md`](https://github.com/gke-labs/kube-agents/blob/main/docs/designs/spec-nats-deployment.md) is canonical for the identity map, the grant sets and how they are derived; this section is the summary.

The chatops gateway spawns a pod for a delegated task, which runs that one task, or for a conversation on its session route, which keeps one pod for the whole conversation. That pod takes each of the conversation's turns, holds its bus credential the whole time, and is reaped at the idle TTL after the last user message, or at the 4-hour maximum lifetime. The idle TTL is 30 minutes by default, and 5 for a DM conversation with one message so far. That pod is where model output actually executes. Any other chat message is answered in the agent pod instead, as [ChatOps](../../site/src/content/docs/concepts/chatops.md#how-a-chat-question-is-answered) describes.

The pod runs as `<agent>-a2a-session`, a KSA that holds **no** Kubernetes RBAC and no Workload Identity binding. The token exists so the message bus can be told who is connecting, not so the pod can talk to the API server or to GCP. A NetworkPolicy denies it the API server anyway, and `automountServiceAccountToken` is false so no default-audience token rides along beside the bus one.

Under the session pods' [cluster view](platformagent-harness.md#the-session-pods-cluster-view) (on by default on the session route, or with the operator's `A2A_SESSION_CLUSTER_VIEW=true`) the pod also projects a second audience-bound token for `<name>-kube-proxy` and the credential broker. `<name>-kube-proxy` accepts that audience from `<agent>-a2a-session` under `read-only-dry-run` mode (`get`/`list`/`watch` with `Secret` redaction, plus server-side `?dryRun=All` validation). The broker maps that audience to a `session` role that reaches its exec route for `gcloud` reads only and refuses every other route and executable. The pod still holds no API-server credential and the ServiceAccount still has no RBAC; the view is the proxy's and broker's, not the pod's.

A session is limited to a small number of concurrent broker commands (`CREDENTIAL_PROXY_SESSION_MAX_CONCURRENT_COMMANDS`, default 2), so it cannot hold the command pool the platform agent's shell shares. Under a `custom` IAM set with an admin role, `<name>-kube-proxy`'s `read-only-dry-run` policy and `Secret` redaction remain the boundary on session `kubectl` calls. The view is a temporary aid until the profile path replaces it.

Every connection to the bus's client listener is TLS. The operator mints a CA and a serving certificate for the bus's Service, the bus refuses a client that connects in the clear, and every client it renders trusts that CA through a ConfigMap carrying its public half. The console's websocket listener serves the same certificate, and the console server dials it verified against that CA; the browser's own leg to the console server is the `kubectl port-forward` tunnel. The certificates renew themselves; a renewal restarts the bus once a year. [`docs/designs/spec-nats-deployment.md`](https://github.com/gke-labs/kube-agents/blob/main/docs/designs/spec-nats-deployment.md#transport-encryption) has the certificate source, the rotation and what happens on upgrade.

Every session pod shares that one KSA, so the KSA alone cannot tell two conversations apart. What can is the pod.

The pod's bus credential is a [projected ServiceAccount token](https://kubernetes.io/docs/tasks/configure-pod-container/configure-service-account/#serviceaccount-token-volume-projection) with a dedicated audience, which the kubelet binds to the pod it mounts it into. When the pod presents it, the bus's auth callout runs a `TokenReview`, and the API server reports that pod's name and UID in fields the client cannot set. The gateway names each pod after the conversation it spawned it for, so the attested pod name is the addressee. The permissions minted for the connection are built from that name: its own task's events, its own three JetStream consumers, its own reply inbox. Nothing else on the bus, including the pods running beside it.

Two consequences worth stating plainly:

- **The model harness can read the credential, and that is accounted for.** The session adapter is PID 1 and the harness is its child at the same UID, so anything the adapter holds — an environment variable, a mounted file — is readable through `/proc`. No amount of care in how the child's environment is built changes that. What changed is not reachability but worth: the credential a harness can lift now authorises exactly the session it is already running as. Before this, every session pod held one shared password that could publish events for any addressee and read the whole task plane.
- **Revocation has two clocks, and the pod is only the first one.** Deleting the pod stops the API server authenticating its token, so a _new_ connection is refused. That is not instantaneous, but it happens within about forty seconds of a zero-grace delete. The API server stops vouching for the token about ten seconds after the delete, which is its own success cache. The bus's auth callout then remembers a successful check for thirty seconds more, so a reconnecting fleet costs one check per token rather than one per attempt. Neither window is the token's one-hour lifetime.
  - A connection that is _already open_ is the second clock and a longer one. The callout signs the grants into a user JWT at connect and the bus holds them until that JWT expires, so deleting the pod does not close the socket. Reaping a session bounds its bus access at the grant TTL, not at the pod's lifetime.
  - This matters much less than it would have before per-session credentials, since the grants a stale session keeps reach only its own already-dead task. But it is the real bound, and shortening it means shortening the grant TTL rather than reaping faster.

Four of the files a kanban worker writes to the agent's volume are redacted inside the image, independently of that gateway switch. Upstream Hermes already formats `agent.log` through its `RedactingFormatter` and passes the terminal-output spill under `cache/terminal-output/` through the same engine. The image adds the worker transcript, because a worker that hand-rolls an authenticated `curl` after a helper script fails otherwise leaves the access token there in plaintext for the hour it is valid.

The `ya29.` access-token shape is registered alongside the engine's built-in credential prefixes, so a bare token is masked wherever the engine runs, not only inside an `Authorization` header. The `💻 $` completion line and the tool preview mask a `terminal` command or `execute_code` source before rendering it.

A worker's stdout and stderr, which the dispatcher points at the board's `logs/<task>.log`, are redacted line by line on the way to that file, and that redaction is forced: `security.redact_secrets: false` does not reopen it. It runs only in a process with `HERMES_KANBAN_TASK` set and a non-terminal stdout, holds a partial line until its newline, and does not see writes that bypass `sys.stdout`.

The audit file the `tool_call_audit` plugin and the `chat_message_audit` hook append to, `logs/audit.jsonl` under each profile, is redacted twice before the write. The emitters themselves run `AuditRedactor` over arguments, results and message text and a pseudonymised principal. Then the sink applies, as one line, the same engine `RedactingFormatter` runs, Hermes' `redact_sensitive_text`, forced so that `security.redact_secrets: false` does not reopen it. The record no longer passes through Hermes' logger, so the formatter itself is not in its path, and the same two layers cover the line an emitter prints to its stdout when the file cannot take it.

The operator's rules, and the session store, follow the gateway switch. With `litellm.redaction.enabled=true` the chart projects the gateway's `redaction.yaml` into the agent pod read-only at `/etc/kube-agents-redaction/redaction.yaml`, and the file's presence there is the switch. The operator admits no path-valued variable through `spec.deployment.env` into the agent container, and the agent cannot write under `/etc`.

The image then runs the operator's IP and named-identifier rules after the credential masking above in every file that masking reaches. It also redacts, through the same forced redactor, what Hermes persists to `state.db` (message content, reasoning and tool calls). The same applies to what the kanban board stores: a card's title and body, a worker's result and summary, a comment's body and a block's reason. Each process reads the rule file once at start: a long-lived process keeps the rules it started with while each new worker process reads the current file, so roll the pod to move them all.

A file that does not parse stops the process at import, as it stops the gateway. The image parses it with the grammar it shipped with, so keep the chart and the agent image at one version when the switch is on. With the switch off, the default, `state.db` and the board are written as before: a command that carried a token is still there verbatim after the transcript has masked it. Nothing already on a volume is rewritten either way, and the OTel plugin's `live.db` is not covered.

A session pod writes its own `state.db` and `agent.log` to an `emptyDir` that lives as long as the pod. The gateway builds that pod itself and does not project the rule file into it, so only the image's credential masking applies there.
