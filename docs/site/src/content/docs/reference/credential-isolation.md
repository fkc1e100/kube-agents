The PlatformAgent shell sandbox receives no API keys, access tokens, or refresh tokens through its environment or filesystem. The one credential it holds is a projected ServiceAccount token bound to the credential broker's audience, which the Kubernetes API server does not accept; the audience is what keeps it from being a general Kubernetes credential. Its ServiceAccount is bound to no Google service account, so the metadata server has nothing to give it either. Credentials live in a trusted **credential broker** that runs as a Pod of its own, and the sandbox reaches credentialed capabilities only through a policy-enforced proxy across the network.

This is the only layout. There is no configuration that puts the broker back in the agent Pod and none that turns the shell sandbox off — `spec.harness.experimental.shellSandbox.enabled: false` is refused with `Degraded`/`ShellSandboxCannotBeDisabled`. The gateway's `platform-agent` container does hold two credentials: the audience-bound token it presents to the broker, and a second audience-bound projected ServiceAccount token for the A2A bus. There is no password: the container names its bus principal in `A2A_BUS_USER` and the bus's auth callout resolves the token to that principal's grants. [The agent now holds a credential](#the-agent-now-holds-a-credential-and-that-was-a-choice) has the trade.

This page summarizes the architecture. The canonical design — including scope, deny-policy details, migration steps, and CI verification assertions — is [`docs/credential-isolation-design.md`](https://github.com/gke-labs/kube-agents/blob/main/docs/credential-isolation-design.md).

`SESSION_KV_API_KEY` and `SESSION_KV_SALT` are `platform-agent`'s only Secret-backed environment variables, and both are pod-scoped: neither opens anything outside the gateway Pod. They cannot sit behind the proxy because that container is the _server_ here.

`session_kv_server.py` binds `127.0.0.1:8699` and needs the key in order to reject callers that are not one of its clients. Those clients are the event watcher, the drift detector, the Platform MCP server, the `incident_context` plugin, the kanban notifier, the chat adapter's scheduled-report relay, the two findings scripts and the `stall-watch` cron script. The salt hashes chat identities before they are written, which has to happen where the identity already is. The design doc has the [full reasoning](https://github.com/gke-labs/kube-agents/blob/main/docs/credential-isolation-design.md#the-loopback-only-exception).

Both are optional in the sense that the pod starts without them, and one of them is not optional in practice. The `k8s-event-watcher` in `agent-api-auth` authenticates with `SESSION_KV_API_KEY` and treats an empty value as fatal, so it exits on every start and no cluster events are watched at all. The container stays Ready, so its log is the only place that says so. The drift detector in the same container fails the same way on the same key, and with the same silence. The Session KV server also answers `503`, and identity hashing falls back to a per-process salt with a warning.

Pod-wide `automountServiceAccountToken` is `false` on every pod (the A2A gateway automounts the token of its own narrow Role, which is the grant it spawns session pods with). Every projected token below expires after one hour:

## Request paths

- **CLI commands** — the sandbox forwards `gcloud` to the broker (while `kubectl` routes through `<name>-kube-proxy`); the broker also runs `git`, and the forge CLI of any configured forge that declares one, on its own behalf for the version-control verbs. The proxy rejects known credential-disclosure, credential-replacement, and self-modification operations, and the GitHub write path (see below); interactive TTY programs, unbounded streaming, sandbox-only file paths, and background processes fail closed.
- **Cloud API reads** — `GET /v1/gcp/<host>/<path>` relays one Google REST read named in `api_policy.API_READ_ROUTES` on the broker's identity, with the caller's headers dropped and the credential-substituting query keys stripped. Today those routes are Cloud Monitoring, Managed Prometheus and Cloud Trace reads, and the GKE cluster list and get the Cluster Agent reconcile makes. One more read is a `POST`: Cloud Logging's `entries:list`, for one project's log entries. The broker checks its JSON body and forwards its own copy of it. Another host, a write, a sibling path or a token endpoint is refused with a `gcp.api.*` rule. `credential_proxy_client.ApiSession` is the client. See [`designs/gcp-api-relay.md`](https://github.com/gke-labs/kube-agents/blob/main/docs/designs/gcp-api-relay.md).
- **Chat** — Slack, Google Chat, and Microsoft Teams adapters send credential-free payloads to Envoy. The credential runtime owns the platform tokens (`SLACK_BOT_TOKEN`/`SLACK_APP_TOKEN`, Google Chat app credentials, and `TEAMS_APP_ID`/`TEAMS_APP_PASSWORD`) and performs the external API calls, enforcing method/host guards, tenant checks, and payload limits. A Slack-armed A2A gateway reads the Slack tokens as Secret-backed env itself and applies `allowedUsers` itself.
- **PlatformAgent API** — the Service targets port 8643 on `agent-api-auth` in the gateway Pod, which validates the external bearer key and forwards to the agent API on loopback (port 8642) with a non-secret sentinel. The real key never reaches `platform-agent`.
- **GitHub** — the broker obtains a Google OIDC identity token and calls [Minty](/kube-agents/deploy/token-minter/), which brokers a repository-scoped GitHub App installation token with a maximum one-hour lifetime. The App's private key stays in Cloud KMS.
- **Watchers** — the event watcher and the drift detector in the gateway Pod's `agent-api-auth` container present the `kubeagents-credential-proxy-watcher` audience. It covers one GKE cluster read and the drift subscription's four Pub/Sub calls under `/v1/watcher/gcp/`, and Kubernetes events, named reads, the event watcher's count lists and one named Pod's metadata under `/v1/k8s/`. The count lists read five cluster-scoped workload kinds, one item each with a metadata-only `Accept`; the Pod read also carries a metadata-only `Accept`. Of that Pod, the broker relays only:
  - its controller ownerReference (the kind, the name and `controller: true`), and only when the kind is one the owner lookup folds on: a ReplicaSet, StatefulSet, DaemonSet or Job;
  - for a ReplicaSet, the `pod-template-hash` label, and only when the ReplicaSet's name ends in `-<hash>`. For any other ReplicaSet, neither the ownerReference nor the label is relayed;
  - never the Pod's name, namespace or UID, another owner, an annotation, another label, `managedFields`, the spec or the environment.
- **Audit-report store** — seven routes under `/v1/audit-reports`, relayed to the store listener in the gateway Pod's `agent-api-auth` container. The broker presents its `kubeagents-audit-report-store` token, read fresh on each call. A body over 1 MiB is refused, no token or body is logged, and the exec tier doesn't serve these routes. On a run write the broker sets `X-Report-Writer` from the caller it verified (`shell`, or `builtin-schedule:<audit>:<task>`) and drops any copy a caller sends. The two report reads answer that header back only while it matches the stored bytes. Three roles reach them:
  - a profile worker reads when its task credential's profile is in `CREDENTIAL_PROXY_REPORT_PROFILES` (`fleet-audit,platform`). It writes only with a builtin trigger named `schedule/<audit>` whose stream is the audit it writes, and only to the repository the audit publishes to, or `no_forge%2Flocal` when there is none. One with no task credential is refused;
  - the sandbox's shell reads every stream and writes the key the audit publishes to (or `no_forge%2Flocal`) or any repository registered in `managed_repos`, as it writes today's file store directly;
  - the A2A gateway's report reader, with its `kubeagents-credential-proxy-a2a-reports` audience, reads one finished report of any audit, `GET /v1/audit-reports/<audit>/publish/latest` or `GET .../publish/runs/<ts>`, on the key the audit publishes to (or `no_forge%2Flocal`) alone. It sends the word `publish` in place of the key, and the broker relays the request with the publish key in its place. Any real key from it is refused, the publish key spelled out included. The broker resolves `publish` for this role only. It never lists the streams, reads a run index, writes or deletes. Only that audience, from the A2A gateway's ServiceAccount, gives this role, and the role reaches no other route.
- **Pub/Sub platform adapter** — four subscription calls (read, pull, acknowledge, modifyAckDeadline) under `/v1/pubsub/gcp/`, presented with the gateway's `kubeagents-credential-proxy-chat` audience and confined to the subscriptions the operator renders from the AgentPlugin configs.

## Guarantee and limitation

**Guarantee:** the operator places no managed credential in the `<name>-shell` Pod's environment, root filesystem, persistent data volume, or ServiceAccount token path. Its ServiceAccount carries no `iam.gke.io/gcp-service-account` annotation, so the metadata server answers it with a principal IAM grants nothing. That is the Pod that runs everything the model wrote.

`spec.deployment.env` goes to the credential broker because it may contain credentials. Only a short allowlist reaches the agent, as literal values only. It holds the OpenTelemetry settings, `EOD_EXCLUDE_NAMESPACES`, the `ALERT_DAILY_LIMIT_*` alert ceilings, the `FEEDBACK_PROMPT_*` switch and delay, and the four findings pacing limits (`FINDINGS_DAILY_CRITICALS`, `FINDINGS_FIRST_REPORT_CRITICALS`, `FINDINGS_NONCRITICAL_AFTER_HOUR`, `FINDINGS_NONCRITICAL_MAX`). It also holds the five `leeway-watch` alert thresholds (`LEEWAY_WATCH_MIN_SEVERITY`, `LEEWAY_WATCH_MIN_DRIFT`, `LEEWAY_WATCH_MIN_MAX_DOMAIN_SHARE`, `LEEWAY_WATCH_MIN_EXCESS_OVER_FLOOR`, `LEEWAY_WATCH_REFRESH_DAYS`), the `INCIDENT_WORKLOAD_DEDUP_SECONDS` window, the `INCIDENT_TRIAGE_OPEN_PULL_REQUEST` switch and its `INCIDENT_TRIAGE_MAX_OPEN_PULL_REQUESTS` limit, the `KUBEAGENTS_ROSTER_SUMMARY_THRESHOLD` roster count, and the `KAGE_SLACK_UX` flag. The `BOOTSTRAP_MAX_CREATES_PER_TICK` reconcile create cap, the two idle thresholds, `CRON_IDLE_HIBERNATE_DAYS` and `CRON_IDLE_THROTTLE_DAYS`, the `CRON_CATCH_UP_STAGGER_MINUTES` catch-up step, the `POST_MERGE_READS_PER_TICK` read cap and the `KUBEAGENTS_EVAL_RUN_TAGS` eval switch reach it the same way.

Two names go the other way and reach the `<name>-shell` Pod, not the agent. `KUBEAGENTS_AUDIT_AUTO_PROMOTE`, the fleet audits' auto-promotion switch, is normalised by the operator to `true` or `false`. `KUBEAGENTS_KUBECTL_COST_TIER`, the column of the shell's kubectl cost table, is passed only as a lowercase word. The tier also goes, normalised the same way, to the A2A gateway as `A2A_KUBECTL_COST_TIER`, and from the gateway to the session Pods it starts under the cluster view as `KUBEAGENTS_KUBECTL_COST_TIER`, since their kubectl runs the same admission.

Three names reach both Pods, each as a file the operator owns: the earned-autonomy switches `KUBEAGENTS_POST_MERGE_CHECK` (`off`, `silent` or `report`), `KUBEAGENTS_AUTOMERGE` (`off`, `practice` or `on`) and `KUBEAGENTS_DIAL` (`off` or `on`). Each is `off` when unset, and any other value reads as `off`. The agent gets them pinned in its managed `.env`, every switch on every render, so a line the agent writes into the PVC `.env` cannot turn one on. The `<name>-shell` Pod's entrypoint writes each to a root-owned file under `/run/kube-agents-sandbox/`. `agents/platform/scripts/kubeagents_switches.py`, their reader in both Pods, takes those files before the variable.

`KUBEAGENTS_POST_MERGE_CHECK`, when not `off`, makes the agent record each fleet-audit `no-pdb` fix pull request it opens for the post-merge check (`silent` and `report` record alike). The `post-merge-check` cron job follows each to a stored outcome; `report` also comments it once on the fix pull request, and a failed run posts to chat.

`automation_rules.py` reads `KUBEAGENTS_AUTOMERGE`. `KUBEAGENTS_DIAL`, when `on`, also reaches the credential broker through `spec.deployment.env`, where it makes the autonomy dial a second source for the write mode ([Explain-only mode](/kube-agents/reference/security-and-iam/#explain-only-mode)). The credential broker reads `KUBEAGENTS_AUTOMERGE` from the same copy of `spec.deployment.env`, unnormalised, so any value but `practice` or `on` reads as `off` there too, before it applies an [auto-merge label](/kube-agents/reference/automation-rules/#the-auto-merge-labels).
Session-kv's `dial_state.py` reads `KUBEAGENTS_DIAL` and runs `automerge_switch.py`, which also reads it and refuses to run without it.

**The gateway Pod holds no cloud identity.** The broker Pod runs as the Workload Identity-annotated ServiceAccount (`spec.security.serviceAccountName`, `kubeagents-platform-agent` by default), and the gateway Pod runs as `<name>-gateway-agent`, which the operator mints with no annotation. GKE resolves Workload Identity by the Pod's ServiceAccount, so the gateway's metadata server has no Google service account to answer for, and the gateway's NetworkPolicy no longer opens the metadata path at all. Everything in the gateway that called Google — the remote MCP servers, the event watcher, the drift detector and the Pub/Sub platform adapter — goes through the broker. [`spec.security.workloadIdentityFederation`](#running-the-shell-in-its-own-pod) remains optional hardening for the broker's own credential.

**The Pub/Sub platform adapter pulls through the broker too.** The `pubsub-platform` AgentPlugin runs in the gateway Pod, so it holds no Google credential. It reads its subscriptions through the broker's Pub/Sub relay, which the operator confines to the subscriptions the AgentPlugin configs name, qualified with the harness project; the broker refuses any other subscription and every other Google API on that route.

The operator fills the relay URL on the gateway and the subscription set on the broker only when at least one plugin route names a subscription it can qualify. That means a full `projects/<project>/subscriptions/<name>` path, or a short subscription or topic name on an agent with a harness project. With no such route the URL is rendered empty rather than left out, so a plugin cannot supply its own, and the adapter does not connect.

**The sharing that made this a container-boundary problem is gone.** The broker is not in a Pod with anything that runs model-authored code, so there is no shared network namespace, no shared process namespace, and no shared writable volume. [`docs/security-requirements.md`](https://github.com/gke-labs/kube-agents/blob/main/docs/security-requirements.md) tracks the requirement formally.

### The agent now holds a credential, and that was a choice

The `platform-agent` container mounts the broker-audience projected token, so the model can read it. A prompt-injected agent gains no new authority _inside_ the Pod, because it could already reach the broker. What it gains is **exportability**: the token is a file, and a file can be exfiltrated, after which an outside party has broker access — bounded by the command policy — until the token expires.

Against the credential requirements this token is short-lived, audience-bound and independently revocable, but **not non-exportable**, and that last clause is the one it misses.

There is a second file with the same property, the `a2a-bus` token. It is bounded more tightly than the broker's: the bus resolves it through an auth callout to the `agent` principal, whose grants are the topic blackboard and nothing else. There is no task plane in either direction, and no JetStream consumer verb at all, so an exfiltrated copy cannot ask the server to deliver a stream anywhere. It replaced a shared static password, which was neither short-lived nor bound to this workload.

**An alternative was considered and deferred.** `agent-api-auth` is already a credential-holding container in the agent Pod, on loopback, at a different UID, with no volumes the agent can read. A mirror image of it — an egress forwarder that holds the token, listens on `127.0.0.1:8765`, and attaches the credential on its way out to the broker Service — would preserve "the agent holds no credential at all". It is not built because it is a new component with its own failure modes and lifecycle, and nothing forecloses it: the client's `authorization_headers()` would return nothing and the forwarder would supply the header instead.

## Running the shell in its own Pod

Everything the agent executes — the wrappers, `execute_code`, and the file tools — runs in a `<name>-shell` StatefulSet reached over SSH. This is not optional: `spec.harness.experimental.shellSandbox.enabled: false` is refused with `Degraded`/`ShellSandboxCannotBeDisabled` and changes nothing about the running workload. [`docs/designs/agent-shell-sandboxing.md`](https://github.com/gke-labs/kube-agents/blob/main/docs/designs/agent-shell-sandboxing.md) is canonical.

`spec.security.workloadIdentityFederation` is the optional hardening on top. With it, the broker takes its cloud identity from an audience-scoped projected token mounted in its Pod alone. The token is exchanged through Workload Identity Federation, whose credential source is a **file path** rather than the metadata server, for an impersonation of the existing Google service account. Without it the broker takes its cloud identity from the metadata server, which answers for the annotated ServiceAccount the broker alone runs as. The design doc has the one-time pool setup, which no install surface performs.
